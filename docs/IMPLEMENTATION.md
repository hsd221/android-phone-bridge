# 技术实现与架构设计

本文档介绍 Android Phone Bridge 的模块职责划分与关键技术选型考量。具体的测试结果与机型兼容性记录见 [测试与设备验收记录 (TESTING.md)](TESTING.md)。

---

## 模块职责划分

项目代码库由三个核心部分构成：

| 模块 | 核心职责 | 依赖与技术栈 |
| :--- | :--- | :--- |
| `bridge` | 负责配对码生成与校验、设备身份散列存储、管理与手机的 WebSocket 长连接会话、请求生命周期与超时调度，并向外部暴露标准 MCP 接口与命令行管理工具。 | Node.js 22+、MCP SDK、TypeScript、ws |
| `android` | 手机端原生应用。通过前台服务保活、主动建立长连接、利用系统无障碍服务实现界面层级解析与手势模拟、获取系统定位、提供权限配置界面。 | Android 11+ (API 30+)、Kotlin、OkHttp、Coroutines |
| `protocol` | Bridge 与手机之间的 WebSocket 通信契约、错误码定义及工具参数规范。 | JSON over WebSocket Schema |

## 关键技术选型与考量

### 1. 手机主动出站连接的架构选择
移动设备在 Wi-Fi 与蜂窝数据网络之间频繁切换，且普遍处于运营商 NAT 或局域网防火墙后方，无法直接作为服务端监听入站端口。  
因此系统采用反向中继架构：
- Bridge 运行在具有固定地址的电脑或服务器上；
- 手机端启动后，主动作为客户端向 Bridge 的 `/device` 端点建立 WebSocket 长连接（生产环境使用 HTTPS/WSS）；
- 手机断网或发生网络切换时，由客户端负责退避重连，外部调用方无需对手机执行内网穿透。

### 2. 身份认证与双重凭证隔离
系统严格区分了两类角色，并实现了凭证的物理隔离：
- **Agent 连接 Bridge**：使用静态的 Harness Bearer 令牌（由 `init` 命令随机生成并保存在本地配置文件中）。
- **手机连接 Bridge**：使用协商生成的设备令牌。首次连接时，在 Bridge 端生成一个 5 分钟有效的临时配对码，手机端输入该配对码完成设备绑定。

绑定完成后的凭据持久化策略：
- **手机端**：将协商获得的长期设备令牌利用 Android Keystore（AES-GCM）进行硬件级加密存储，且显式禁止系统云备份（`allowBackup="false"`）。
- **Bridge 端**：本地状态文件（`bridge-state.json`）仅保存该令牌的 SHA-256 散列值，不持久化明文。即使 Bridge 宿主机的存储文件泄露，外部攻击者也无法反向推导出原始令牌。
- **单设备绑定原则**：首版设计严格支持一台 Bridge 绑定一部手机，避免多设备争抢控制权引发状态混乱。

### 3. 原生无障碍截图与界面感知机制
- **避免录屏推流（MediaProjection）开销**：传统推流方案在后台维持推流编码会带来严重的发热与电量消耗，且系统会频繁弹出安全确认弹窗。自 Android 11（API 30）起，系统无障碍服务原生提供了 `takeScreenshot` 接口，按需单次捕获屏幕快照即可满足感知需求，轻量且无需持续推流。
- **多窗口安全检查与污染防护**：在解析 UI 树或截图时，服务会校验当前屏幕上的所有可见窗口。若检测到存在未经授权的应用窗口、锁屏页面或系统安全窗口（例如输入密码时的安全键盘），操作将被直接防御性拦截，防止敏感信息外泄。

### 4. 权限控制与请求调度语义
- **默认拒绝策略（Default-Deny）**：所有能力开关（定位、读屏、截屏、手势操作）及具体应用的访问权限在初始化时默认全部处于禁止状态，需用户在手机端手动开启，且“读取”与“操作”权限相互独立配置。
- **严格串行与超时机制**：手机端在任何时刻仅串行执行一个动作，队列最多容纳 8 个待处理请求。每个请求均携带全局唯一 UUID 与绝对过期时间戳（默认 30 秒超时）。若网络延迟导致请求延期到达，或排队过久超时，手机端会立即丢弃，**在网络恢复后绝不重放变动操作**，防止产生非预期的二次副作用。
- **操作不确定状态标记（`outcomeUnknown`）**：若手势指令已提交给 Android 系统内核，但中途由于网络中断未能收到系统的执行确认回调，Bridge 会向 Agent 返回 `outcomeUnknown: true`，明确提示调用方当前状态未明，禁止盲目重试。

### 5. 设备基础与 Shizuku 增强
- **设备基础与暂缓 Root**：绝大多数日常主力机均未 Root，且当前开发环境缺乏具备 Root 权限的真机用于充分测试验证，因此系统以普通未 Root 设备为基础，暂不提供 Root 路径，待未来具备测试条件后再行评估。
- **ADB 与 Shizuku 纳入规划**：ADB 与 Shizuku 属于既定系统能力规划。在免 Root 前提下，原生无障碍后台调起某些应用时可能较慢或受系统限制，Shizuku 作为可选的受限 UserService 增强，用于显式应用启动和本地解锁。即使设备未安装或未运行 Shizuku，基于原生无障碍服务的所有核心功能依然完全独立可用。
- **通用 Shell 延后引入**：通用命令行入口具有极高的系统风险，必须配套专门、独立的权限审查机制。为了收敛首版验证范围并守住安全底线，首版不提供任意 Shell 执行入口，留待后续版本逐步引入。

### 6. 手机本地解锁

开启 Shizuku 增强且 shell UID 2000 的连接已授权时，`ShizukuUnlockService` 优先处理本地凭据输入。它通过 `UiAutomation` 读取手机本地系统锁屏，数字 PIN 使用已核验数字键边界内的触摸事件，密码使用系统密码框动作，图案注入核验九宫格内的连续触摸事件。不启动 `adb` 连接或命令行解释器，不接受任意命令、控件或坐标；凭据只通过同 APK 的本地 Binder 使用，不进入命令行、Intent 或网络。服务限制调用方为本应用 UID，拒绝 Root，结束时断开自动化连接并退出进程。

Shizuku 和无障碍共用 `KeyguardUi` 的系统归属、默认显示器、相交覆盖窗口及空输入校验。解锁期间包含不重要但可见的无障碍控件，便于核对厂商隐藏在精简树之外的控制；结束后恢复原无障碍标志。Shizuku 自动化连接不抑制现有无障碍服务。连接或预检阶段确认不可用时，释放 shell 服务并对新取得的系统窗口执行无障碍预检；安全拒绝和取消不触发降级。持久尝试标志在任意凭据动作前写入，之后断开、失败或结果不明均停止，不切换路径重输。Shizuku 成功返回 `path: "shizuku"`，无障碍凭据成功返回 `path: "local_credential"`。

`phone_unlock` 只接受空对象。它同时要求操作能力、独立的本地解锁授权以及未暂停的访问状态。`UnlockActivity` 是不导出的短时安全窗口，锁屏凭据不经过 Intent。未配置本地凭据时，窗口负责唤醒并请求 Android 系统消锁；无安全锁或系统信任允许消锁时，由 Android 直接处理。配置了本地凭据时，窗口仅唤醒手机，随后直接进入已核验系统界面的本地输入流程，避免部分厂商系统隐藏验证界面时的取消回调阻断流程。

手机已亮屏且已有验证控件时，直接核验系统界面，不打开可能隐藏键盘并清掉已有输入的临时窗口。如果仍处于锁屏壁纸且没有已知输入控件，`LocalUnlocker` 会结束临时唤醒窗口，在核对的系统锁屏窗口内执行一次固定上滑，再等待验证控件。上滑不包含凭据，也不接受远端坐标；已有验证控件、解锁请求已取消或滑动区域被其他窗口覆盖时不会上滑。唤醒窗口的返回键和“取消本次解锁”按钮会明确取消本次请求；程序主动交还系统锁屏不会被当成用户取消，过期窗口的系统回调也不会修改新请求状态。

需要凭据时，`LocalUnlocker` 仅识别系统应用中的已知锁屏容器：数字 PIN 点击系统键盘，文字密码使用密码框的设置文字与 IME 确认动作，图案在已核对的系统九宫格边界内派发单条手势。每次输入前重新检查锁屏归属、覆盖窗口、取消、期限与权限。上滑前后也检查取消与暂停；未识别键盘时明确返回 `UNLOCK_UI_UNAVAILABLE`，不会开始凭据输入。未识别的方式、已有输入、生物识别要求或异常窗口会停止流程并要求用户处理；不提供凭据猜测或系统认证绕过。

PIN 默认使用已识别的 `key_enter` 确认；仅在该控件不存在时，才检查已知 MIUI 自动确认布局。这个分支仍要求受保护的 `pinEntry`、已知容器、十个唯一且可点击的 `key0` 至 `key9`，并逐一核对数字无障碍标签。已核对的 MIUI 控制器在空输入时显示 Back；旧布局标识为 `back_button`，较新的布局为 `cancel_button`。只接受系统锁屏内这两个准确标识中唯一可见、启用且可点击的控件；多个可见候选、不可用控件或任何可见 `delete_button` 均拒绝输入。删除键不存在或输入框文本为 null 本身不能证明输入为空。

首键前再次核对空态，后续每键要求两个已知 Back 标识均不可见且 Delete 可用；任一 Back 重新出现、系统清空输入或进入无法核验的状态时，停止余下按键，避免本地配置过长时再次触发自动验证。输入过程中逐键重新核验系统窗口、受保护输入框与数字标签，最多输入本地配置的一次序列，然后只等待系统确认，不猜测确认动作。已存在但不可用的确认键不会改走自动确认。该兼容分支不按按钮文字推断标识、不点击 Back/Cancel，也不主动清空用户已有输入。`back_control_*` 固定诊断表示这两个已知空态控件的查询结果。

`LocalUnlockStore` 使用独立的 Keystore AES-GCM 密钥和私有存储，凭据不参与 Bridge 序列化。首次输入前持久写入尝试标志，仅在确认系统解锁成功后清除；失败、取消或进程退出后继续阻止自动输入，须用户在解锁后的本地设置页检查恢复。解除配对会删除本地凭据及其密钥，并关闭解锁授权。普通远程读屏、截图和交互仍拒绝锁屏及本应用界面。保存凭据不修改独立解锁授权，保持用户当前的开关选择；删除凭据仍会关闭授权。

`phone_status.unlock.lastAttempt` 提供最近一次解锁的固定阶段、结果码、唤醒模式、拒绝原因和是否开始展示手势或凭据输入。拒绝原因仅使用预设枚举，区分输入框、数字键、确认键与空输入状态等检查。记录仅存在进程内存，关闭独立解锁授权或解除配对时清空；它不包含异常正文、节点、屏幕内容或任何凭据信息。

## 隐私与数据安全保障

- **Bridge 端无敏感数据持久化**：Bridge 仅作为无状态协议转换与请求调度层，手机端回传的屏幕快照、截屏图片、GPS 坐标以及用户输入的文本，绝不写入 Bridge 的日志文件或本地磁盘。
- **防反向操控保护（`FLAG_SECURE`）**：手机端的主应用与设置页面强制启用了系统 `FLAG_SECURE` 属性，且代码层面硬编码禁止远程操作自身包名，杜绝了 Agent 远程查看或篡改自身权限配置的可能。
