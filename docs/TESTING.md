## 一、自动化测试与执行命令

在提交代码或发布前，可以通过以下命令跑完所有静态检查、单元测试与集成测试：

### 1. 全量检查命令
```sh
# 依赖安装与类型检查
npm ci
npm run check

# 执行 Bridge 服务端测试
npm test
npm run build

# 执行 Android 原生端单元测试、Lint 与打包构建
cd android
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleDebugAndroidTest :demo:assembleDebug
```

### 2. 测试覆盖内容
- **Bridge 服务端测试**：
  - 测试套件会在本地临时启动真实 HTTP 与 WebSocket 监听；
  - 使用官方 MCP SDK 客户端分别走 Streamable HTTP 与 stdio 发起请求；
  - 覆盖场景：一次性配对码、凭据持久化与单向撤销、Harness/手机身份隔离、Host/Origin 校验、请求参数校验、超时取消、迟到响应丢弃、断线不重放等。

## 二、Android 模拟器端到端自动化闭环

针对完整的调用链路，项目提供了自动化模拟器端到端测试脚本。脚本会自动安装 APK、配置无障碍与测试权限、启动 Bridge 并通过 MCP 客户端跑通完整交互流程。

> ⚠️ **运行前提**：  
> **模拟器测试脚本仅允许在专用、干净的测试模拟器上运行**。脚本要求显式传入 `emulator-*` 编号，执行中会重置应用数据并注入模拟定位，**严禁在个人日常使用的手机上运行**。

### 1. 运行常规端到端闭环
在已启动 Android 15 (API 35) 官方 x86_64 模拟器的情况下执行：

```sh
# 基础端到端闭环测试（覆盖权限 UI、状态刷新、UI感知、手势交互与断网重连自愈）
npm run test:android -- emulator-5554

# 包含 Shizuku 增强路径的完整闭环测试（需模拟器内已安装并启动 Shizuku）
npm run test:android -- emulator-5554 --shizuku
```

- **权限管理专项测试 (`PermissionManagementTest`)**：自动化脚本会优先执行三组权限 UI 测试，覆盖应用搜索、跨筛选多选、页面重建/屏幕旋转、四类批量操作以及“一键全开”的影响范围，测试结束后会自动清理沙箱数据。
- **断网恢复自愈验证**：测试过程中会自动切断模拟器的 Wi-Fi 与数据网络，并在稍后恢复，验证 APK 在不重新打开页面的情况下能够自动重新连接 Bridge 并继续响应后续的 MCP 调用。

### 2. 开机冷启动恢复测试
```sh
npm run test:android:boot -- emulator-5554
```
- 该脚本在模拟器注入测试配置后直接触发 `adb reboot` 重启系统；
- 重启后在**完全不打开主 APK 界面**的前提下（仅模拟用户解锁了无 PIN 密码的测试机），由主机端独立的 MCP 客户端发起轮询，验证 `BootReceiver` 能否在后台拉起 `BridgeService`、通过 Keystore 自动恢复连接，并验证无障碍、定位前台服务及后台拉起测试应用的能力。

## 四、物理真机人工验收标准步骤

如果你拿到了一台物理 Android 手机准备接入使用，建议按照以下 10 步进行功能验收：

1. **服务启动与配对**：按照部署说明启动 Bridge 并接入 MCP Harness；在 Bridge 生成配对码，安装主 APK 并输入配对码完成初次绑定。
2. **默认安全策略校验**：在未开放任何能力开关前，通过 Harness 调用 `phone_status` 确认基础诊断工具正常可用（该工具豁免能力限制）；随后调用 `phone_location`、`phone_ui` 等能力工具，确认请求被手机端以 `CAPABILITY_DENIED` 拦截。
3. **系统权限与能力开启**：在手机端依次开启无障碍服务、精准定位及前台通知权限；对于 Android 15 或厂商深度定制系统，根据报错提示将桌面 Launcher（如 `com.android.launcher3` 或厂商桌面）及系统状态栏（`com.android.systemui`）加入可见白名单。
4. **独立测试应用交互校验**：安装附带的 `demo-debug.apk`，在权限管理中赋予其读取与操作权限。通过 Agent 执行：打开应用 ➔ 读取 UI 树 ➔ 在输入框写入文本 ➔ 模拟点击确认按钮 ➔ 重新读取界面核对内容。
5. **安全边界拦截校验**：在手机切换至未授权应用、弹出输入法软键盘或处于受保护界面（包含密码输入）时尝试截屏或点击，确认操作被防御性拒绝。
6. **随时暂停控制**：在手机端通知栏点击“暂停操作”，确认 Agent 的读取请求正常但写操作被拒；点击“暂停全部”，确认除基本状态诊断外所有能力均被拒绝。
7. **复杂网络切换与防重放**：在 Agent 执行长时间或排队操作过程中人为断开手机 Wi-Fi 或切换至蜂窝网络。确认未完成的变动指令不会在重新连通后被盲目重放。
8. **解绑机制验证**：在手机端点击“解除配对”，确认原有连接立即关闭且历史凭证无法再次建立连接；在离线状态下解绑，验证设备侧即刻切断本地一切外部访问。
9. **可选 Shizuku 增强测试**：在设备上配置好 Shizuku，通过手机端开启增强开关，验证 `phone_status` 是否正确报告 UID 2000，以及通过 Shizuku 调起应用的路径。
10. **多机型兼容性记录**：记录当前测试设备的具体型号、ROM 版本、耗时表现及系统电池优化设置，为后续机型适配积累数据。

## 五、当前系统边界与说明

1. **不越权**：系统坚决不使用任何 Root 提权漏洞、不开放通用 Shell 终端入口、不支持后台静默爬取短信相册或跨应用读取私有数据库。
2. **依赖无障碍可见性**：UI 树解析完全基于系统的 Accessibility API，若目标应用对无障碍隐藏了节点或处于安全受控状态，Agent 将无法感知该区域。
3. **无障碍非事务性**：Android 系统的原生手势调度是非事务性的，一旦指令派发给系统底层便无法物理撤回。在将敏感 App 纳入白名单前，建议先在测试 App 中充分验证。
4. **定制 ROM 的后台机制**：由于各大厂商对后台进程、自启动与省电策略的限制差异巨大，物理真机若要保持长期后台可用，必须由设备使用者在系统设置中手动开启“允许自启动”并关闭“电池激进优化”。

## 七、0.3.0 本地解锁验收

专项使用独立测试模拟器，运行命令为 `npm run test:android:unlock -- emulator-5554`。脚本只允许 `emulator-*`，会清除测试应用数据，并临时设置、移除模拟器内生成的合成锁屏凭据；不得用于个人设备。合成凭据只在模拟器本地生成与使用，不作为 Bridge 参数传输。

已在 AOSP Android 15 / API 35 模拟器完成：无密码消锁、数字 PIN、文字密码与九宫格图案的真实 MCP 解锁；默认拒绝、独立授权、两级暂停、普通全开不启用解锁；凭据密文存储、安全配置页、重建不恢复输入草稿、解绑清除；错误凭据的一次输入与取消后持久阻止重试、手动解锁不自动解除阻止、本地恢复后再次解锁。Bridge 测试另行验证拒绝凭据参数、操作类 MCP 标记、断线不重放与取消结果。

测试 APK 内的独立包无障碍覆盖窗口与凭据区域相交时，解锁在任何输入前被拒绝，不写入尝试标志；移除覆盖窗口后可正常解锁。测试夹具不进入交付的主 APK。

0.3.0 发布前的成功结果仅覆盖上述 AOSP 镜像，不代表实体手机、MIUI/HyperOS 或其他厂商 ROM、图案以外的自定义锁屏与生物识别硬件的兼容性。后续实体设备首测见下一节。指纹、人脸和重启首次解锁由用户在系统界面完成；未识别的锁屏保持手动解锁路径。

## 八、0.3.0-pre.2 验证界面展示回归

0.3.0-pre.1 在一台实体设备的首次锁屏测试中仅成功亮屏，返回 `UNLOCK_UNSUPPORTED`，未开始 PIN 输入。用户观察到仍为锁屏壁纸、未出现数字键盘。0.3.0-pre.2 增加核对系统窗口后的单次本地上滑。随后在 HyperOS 设备复验时仍只亮屏，约三秒后返回 `USER_UNLOCK_REQUIRED`；状态确认未开始凭据输入。原验证只记录结果码，无法从该次证据唯一确定是系统消锁取消还是输入框预检查拒绝；上述两个版本均没有实体设备解锁成功的验证结果。

`npm run test:android:unlock -- emulator-5554` 同时运行 `UnlockTest` 与 `UnlockBouncerTest`。pre.2 的后者在进程内禁止自动系统消锁以稳定复现仅壁纸状态，再验证 PIN、密码和图案均通过一次上滑展示控件并完成本地解锁。测试还覆盖：上滑前后取消或暂停均不输入凭据、不写入尝试标志；已有 PIN 键盘时不额外上滑；相交第三方无障碍覆盖窗口及未知锁屏前台窗口在手势前被拒绝。测试设置不通过 Intent、偏好或 MCP 暴露。

测试还发现临时唤醒窗口结束后，无障碍窗口根可能短暂为空。实现会在两秒内只读等待可核验的系统窗口，保留窗口大小、系统归属和相交覆盖检查；超时不会按猜测坐标滑动。上述新增分支已在 AOSP API 35 模拟器通过，厂商真机仍需安装修复包后验证。

## 九、0.3.0-pre.3 默认唤醒路径与取消回归

`UnlockBouncerTest` 直接使用正式代码的默认路径，移除 pre.2 中控制系统消锁的测试参数。测试检查配置本地凭据后选择仅唤醒窗口，PIN、密码、图案各通过一次核验后的上滑展示控件；未配置凭据时保留系统消锁，无安全锁的系统消锁也由原 MCP 闭环检查。

已有系统验证界面时不再打开临时窗口，避免已有输入被隐藏或清空。回归检查调用前已存在的部分 PIN、密码输入保持原样且被拒绝，空键盘可直接使用；唤醒窗口的返回键与本地取消按钮、请求取消、暂停均在后续凭据动作前停止。原有相交窗口、未知前台窗口与失败后持久阻止重试检查继续保留。

pre.3 的 `phone_status.unlock.lastAttempt` 回归限制为五个固定状态字段，检查成功、失败、取消、输入前拒绝和解除配对后清空；不输出合成凭据、节点或屏幕文本。

pre.3 安装后在 Redmi K70 / HyperOS 3.0.307 进行一次实体测试，确认使用 APK 0.3.0 / versionCode 6。手机从灭屏进入 PIN 面板，但预检查返回 `UNLOCK_UNSUPPORTED`，`credentialAttempted=false`，未开始输入，也未触发重试阻止。该版本的固定状态只能确定停止在预检查，不能唯一定位具体控件；仍没有该实体设备解锁成功的验证结果。

## 十、0.3.0-pre.4 自动确认 PIN 检查

新增的布局模型单测覆盖已核对的 MIUI 空键盘、缺少 Back、可见 Delete、缺键与重复键、不可点击数字、不精确或与键标识不符的数字标签等接受和拒绝边界。单次输入执行器单测使用合成值与假的动作适配器，检查自动确认不派发 Enter、显式确认仅一次、已解锁或中途解锁时早停，以及取消、撤权、动作失败或适配器拒绝后的停止与不重放。输入状态检查还覆盖系统在前缀自动验证后清空输入的情况，确保本地配置余下数字不会在重置后的键盘上继续输入。

两套 AOSP 解锁回归继续覆盖 PIN、文字密码、图案、无凭据系统消锁、已有部分输入、相交覆盖窗口、取消与持久重试阻止，并将最近尝试状态限制为六个字段和固定 `reason` 枚举。这些测试不伪造系统窗口归属，也不修改正式代码的信任检查。AOSP 镜像不能代替 MIUI 的自动确认键盘；新增自动确认分支的验证范围为模型与执行器单测，HyperOS 实体解锁结果仍待安装此版本后验证。
